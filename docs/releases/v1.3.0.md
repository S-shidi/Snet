# SNET v1.3.0

> Release notes for `v1.3.0`. Relay v2 remains disabled in production for this
> deployment; enabling it is a separate flag day after every client is upgraded.

## Added

- Relay v2 direct paths over the same LAN and global IPv6, with independent
  v4/v6 UDP sockets and `lan > ipv6 > public` path priority.
- `PUT /api/v1/networks/{nid}/nodes/{nodeID}/direct-endpoints` and
  `/ctl` support for publishing direct endpoints and advisory NAT type.
- Multiple Relay v2 endpoints via `SNET_RELAY_V2_ENDPOINTS`; clients maintain
  HELLO/PING sessions and direct registration on every advertised relay.
- Per-source-IP token-bucket limiting for Relay v2 control frames plus
  `snet_relay_control_drops_total`.

## Changed

- `/ctl/status.relayPath` exposes `relayCandidates`, `relayReady`,
  `relayIndex`, NAT type, and per-peer direct candidates.
- Relay v2 clients prefer the first ready relay for outbound traffic and fail
  over immediately to another ready instance; a failed instance reconnects
  independently without dropping healthy relay sessions.
- `scripts/rollout-vps.sh` and deploy docs support comma-separated Relay v2
  endpoints.

## Fixed

- Relay dial/DNS failures, HELLO timeouts, and silence affect only the failed
  link instead of rotating the whole client away from other working relays.
- Relay sessions stay registered on all advertised instances, so clients that
  select different relays can still exchange relay traffic across instances.
- IPv6-only direct maintenance no longer stops while the IPv4 direct socket is
  absent; public-path changes clear stale hint IPs; control buckets are capped.

## Compatibility

- Product version: `1.3.0`
- Coordination `APIVersion`: `1`
- Minimum client: `v1.2.0` for regular coordination APIs. Relay v2 requires every
  network member to run `v1.2.0+`; mixing old and Relay v2 clients is not
  supported after the flag day.
- `v1.3.0` server can be deployed with Relay v2 disabled; this release's
  production rollout keeps it disabled.

## Upgrade order

1. Coordination server (`snet-server`) — safe with Relay v2 still disabled.
2. SDserver / NAS clients.
3. VPS client container (if used; VPS is server-only today).
4. Desktop, Android, and Windows clients.
5. Only after every client reports the new version: enable
   `SNET_RELAY_V2_ENDPOINT`/`SNET_RELAY_V2_ENDPOINTS` + `SNET_RELAY_SECRET`.

## Known issues

- Relay v2 LAN/IPv6, NAT rebinding, multi-relay failover, MTU, and throughput
  still need four-node hardware testing.
- Docker bridge clients use ephemeral direct-socket ports; same-LAN direct
  connectivity needs host networking, explicit DNAT, or extra port mappings.
- `DefaultMTU` remains `1320` (safe, below the 1400/1420 target).
- Android release signing and Windows installer verification still depend on CI
  secrets/manual checks.
